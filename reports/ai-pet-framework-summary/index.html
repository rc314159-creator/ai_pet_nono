DISCUSSION FRAME

我们讨论的框架

讨论不是从功能清单开始，而是按“定位、受众、板块、分工”的顺序收敛。这个顺序很重要：只有先定产品为什么存在，后面的硬件、AI、换装、电商才知道该服务谁。

1

先定产品定位

在“宠物出发”和“人出发”之间做选择。结果更倾向从人的情感陪伴需求出发，再把宠物数据和硬件能力作为增强层接入。

2

再定目标受众

用户被分成两类：已经有真实宠物的人，以及没有真实宠物但需要陪伴和互动的人。两类用户共用宠物形象，但任务不同。

3

然后拆产品板块

围绕 AI 聊天、真实数据绑定、健康解释、照护记录、纯电子宠物养成、换装电商和多端入口拆分功能。

4

最后定分工和节奏

真实宠物方向继续细化需求和数据；纯电子宠物方向细化玩法和留存；技术方向找开源项目、桌面端和通讯软件接入方案。

PRODUCT TAXONOMY

目前形成的产品分类

现在的产品不是单点功能，而是一个双主线产品：真实宠物关联解决“我想更懂自己的宠物”，纯电子宠物解决“我想要低门槛陪伴”。中间的共享能力决定技术和内容资产能否复用。

BRANCH A

真实宠物关联主线

面向已经养宠物的人，把真实宠物档案、行为数据和照护记录转换成可解释、可互动、可提醒的 AI 宠物。

  • 宠物档案物种、品种、年龄、体重、健康史、饮食偏好、外观特征。
  • 数据绑定手动记录、CSV/mock 数据、未来可接项圈或手环设备。
  • 照护任务喂食、换水、遛狗、清洁、梳毛、用药提醒和异常观察。
  • 健康解释把一周或一个月的数据变成报告、趋势、异常提示和问诊证据。
  • 安全边界给风险提示和就医建议，不替代兽医诊断，不自动处方。

共享能力层

两条主线不应各做一套。真正要沉淀的是 AI 对话、记忆、状态、形象、推荐和多端入口。

AI 聊天 宠物记忆 状态机 桌宠表达 商品推荐 Web/桌面/通讯软件
BRANCH B

纯电子宠物主线

面向没有真实宠物但有陪伴需求的人，提供一个可聊天、可养成、可互动、可装扮的 AI 虚拟宠物。

  • 陪伴聊天用户不是查百科，而是在和一个持续存在的宠物角色建立关系。
  • 养成成长状态、亲密度、习惯、任务和升级构成长线留存。
  • 互动玩法喂养、玩耍、清洁、训练、日常陪伴和桌面反馈。
  • 换装定制电子服装、宠物形象、现实同款和定制商品形成商业入口。
  • 社区挑战排行榜、分享、挑战和活动可作为后续扩展，不进入第一版核心闭环。

CURRENT RESULT

目前讨论结果

现有实现和文档更适合把“真实宠物数字分身”作为第一版演示闭环。这样既能利用已有 OpenPets、mock 数据、照护任务和商品推荐，也能在汇报中说明它属于更大的 AI 情感陪伴产品。

01用户创建真实宠物档案，系统生成或选择匹配的虚拟宠物形象。
02手动记录和 mock 设备数据驱动活动、睡眠、心率、体温、GPS、安全围栏等状态。
03AI 基于宠物档案和最近数据生成今日照护任务、健康趋势解释和异常提示。
04桌宠窗口和 Web 控制台展示宠物状态、气泡提醒和用户互动反馈。
05库存不足或任务需要时触发商品推荐，但保留人工确认，不做自动下单。
06汇报叙事中补充纯电子宠物主线，说明后续可复用同一套共享能力层。

MVP 的边界

不把第一版押注在真实硬件 API、自研桌宠 runtime、兽医诊断、复杂社区或自动购买上。第一版重点是演示完整闭环。

CAPABILITY MAP

功能板块怎么拆

功能不按“好不好玩”散列，而是按价值链分类：先建立关系，再接入数据，再解释照护，再承接商业化，最后扩展渠道和社区。

入口

AI 宠物聊天与陪伴

用户通过对话、状态反馈、气泡提醒和桌宠表达建立持续关系。

证据

真实宠物数据绑定

档案、喂养、饮水、睡眠、活动、心率、体温、GPS 和行为异常。

解释

健康与照护报告

不只展示数字，而是生成趋势、异常原因、照护建议和就医提示。

留存

纯电子宠物养成

聊天、互动、状态成长、任务、升级和排行榜形成持续使用理由。

商业

换装与电商推荐

虚拟试装、同款推荐、定制宠物服装和用品推荐成为转化入口。

渠道

多端陪伴入口

桌面端和 Web 先跑通，后续再考虑飞书、微信等通讯软件接入。

KNOWLEDGE BASE

知识库该怎么分类

KB 不是资料仓库，而是项目决策缓存。分类上要把“当前真相”和“证据材料”分开，把产品 taxon 和技术 taxon 分开，再用 INDEX 做入口。

当前真相

product / architecture / modules

产品定位、受众、功能边界、架构裁决和模块契约属于权威 spec。

证据来源

research / meetings / verification

调研、会议记录和运行报告支撑判断，但不能直接替代当前 spec。

执行过程

plan / fix-records

计划记录步骤和验收标准；问题记录保存时间线、根因、修复和验证。
