# AI Pet MVP 功能设计对齐

## 来源

本文件根据 `docs/会议记录/MVP功能设计与产品讨论.txt` 和用户后续明确纠偏整理。

当前必须纠正的口径：项目没有 HTML 展示页，不做静态网页看板，也不把浏览器页面作为产品第一入口。技术上可以使用前端技术渲染窗口，但产品形态是桌面宠物系统。

## 产品一句话

AI Pet 是一个连接人与宠物的情感陪伴 agent。桌宠是用户第一眼看到和点击的主入口；点击桌宠后弹出应用窗口，承载陪伴聊天、数据监测、异常报告、换装互动和后续社区/商业入口。

## MVP 用户与宠物范围

- 核心定位：情感陪伴优先，健康解释和真实宠物数据服务于陪伴闭环。
- 真实宠物用户：优先模拟有猫狗的上班族。
- 无真实宠物用户：可以领养纯电子宠物，偏向陪伴、养成和玩法。
- 物种范围：MVP 先支持猫和狗，异宠不进入当前闭环。
- 真实宠物和电子宠物共用同一套宠物档案、状态、对话、窗口和桌宠表达；核心差异只在数据来源。
- 真实宠物数据来自设备、mock 设备和人工记录；纯电子宠物数据来自用户设定、算法生成和互动事件。
- MVP 默认一人一只当前宠物；多宠物、群聊和多角色可预留，不作为当前必须实现。

## 产品入口与窗口形态

### 主入口

- 用户启动系统后先看到桌面宠物。
- 桌宠负责常驻、轻提醒、气泡、异常提示和点击入口。
- 桌宠不是 HTML 页面，也不是网页里的装饰组件。

### 点击后的应用窗口

- 用户点击桌宠后，弹出应用窗口或功能面板。
- 这个窗口是产品交互主体，承载所有复杂操作。
- 可以用 React/Vite 等前端技术实现渲染，但对产品和汇报口径统一称为“应用窗口”“功能面板”或“宠物面板”，不称为 HTML 展示页。
- 应用窗口视觉比例按手机屏幕长宽比设计，当前 demo 采用约 `430x932` 的竖向比例；不要再做宽屏控制台式布局。
- 窗口最小化或关闭后，关键状态、装扮和提醒要同步回桌宠。
- 当前执行分工是：桌面端宠物形象由另一条开发线处理；本线只负责点击桌宠后打开的应用窗口/功能面板。应用窗口里的宠物分身只承担背景板或视觉占位，不投入桌宠形象制作。

### 桌宠交互边界

- 桌宠本体只承接轻交互：点击、气泡、异常提示、简单状态表达。
- 大型交互不直接在桌宠身上完成，例如换装、数据查看、异常分析、长对话。
- 用户点击桌宠进入窗口后完成复杂操作；操作结果再反馈到桌宠形态、气泡或状态。

## 应用窗口信息架构

MVP 点击桌宠后默认进入陪伴对话主页。底部或等价导航保留 3-4 个主入口：

1. 陪伴对话主页。
2. 状态与数据。
3. 换装/互动。
4. 后续社区和商业入口。

当前 MVP 先把社区和电商从核心闭环中拿掉或做入口预留，不让它们阻塞桌宠、对话、数据和异常闭环。

## 陪伴对话主页

- 主页是陪伴聊天，不是数据看板。
- 主页应是类似微信的纯上下文聊天窗口，不混入今日状态、数据卡片或异常报告。
- 一个宠物对应一个连续对话上下文。
- 对话需要维护用户记忆和宠物记忆。
- 宠物可以主动发起消息，例如异常求助、长时间未互动后的问候、日常陪伴提醒。
- 用户也可以主动点击桌宠进入对话。
- 对话可以同时支持文字输入、语音输入、文字输出和语音输出；语音不是 MVP 阻塞项。
- 真实宠物分身应作为对话背景板出现，作为对话对象和情感陪伴视觉主体；不能以侧边栏方式占据聊天页。换装结果要能反映在这里。

## 数据与异常

### 原始数据模型

MVP 使用 mock 数据模拟硬件和人工记录。数据应分清原始数据、二级指标和 AI 解释：

- 原始数据以时间序列为主，例如心率、呼吸、体温、运动、睡眠、定位和行为状态。
- 进食可以记录食物类型、进食量、进食速度和频率；采集方式可来自硬件假设、喂食设备或人工输入。
- 睡眠记录睡眠时长、夜间醒来次数和睡眠质量。
- 运动记录运动时长、活动量、运动模式和长时间不动。
- 定位记录 GPS 或室内定位状态。
- 动物特殊行为记录舔毛、抓挠、吠叫、排泄、异常徘徊等事件。
- 清洁、洗澡、护理、用药等很大程度依赖人工日历和手动记录。

### 展示口径

- 用户看到的不是原始数据流水账，而是“正常/异常/需要关注”的状态。
- 今日状态和数据必须在同一个状态与数据页面展示；不要把今日状态拆成侧栏或单独页面。
- 状态与数据页面可以展示摄食、运动、睡眠、定位、特殊行为和护理记录。
- 数据变化要能影响桌宠形态，例如睡觉、疲惫、异常警告、开心等状态。

### 异常触发

MVP 至少支持以下 demo 规则：

- 进食量相对基线明显增加或减少，例如变化 20%。
- 长时间未进食。
- 长时间不动或运动量明显下降。
- 睡眠时长或夜间醒来次数异常。
- 抓挠、舔毛、吠叫等特殊行为频率异常。
- 位置或安全围栏异常。

异常发生时，桌宠弹出气泡或提示。用户点击异常提示后进入异常报告视图。

### 异常报告和建议

- 通知的是异常，不是孤立建议。
- 每条异常至少对应一条 AI 分析和一条处理建议。
- 异常报告应解释：发生了什么、为什么异常、相关历史数据、建议观察或行动。
- 建议可被用户确认、忽略或标记已处理，并保留历史记录。
- 健康问答或问诊入口优先放在异常报告和数据视图中，不强行塞进陪伴私聊。
- 真实医生或外部问诊可以作为后续入口；MVP 先做 AI 解释和建议。

### 定期报告

- 正常情况下提供定期数据总结，例如周报、月报或周期健康报告。
- 报告应汇总稳定指标、异常历史、行为趋势和照护建议。

## 换装与互动

- 换装是娱乐和陪伴玩法，不是当前电商商品页面。
- 换装入口可以独立于对话主页，避免用户不知道该功能存在。
- 换装内容优先使用内置模板：服装、帽子、鞋子、配饰、简单妆容或装饰。
- 宠物核心身份应固定，尤其是真实宠物分身不随意改变五官、体型和基础形象。
- 换装完成后，结果要同步到对话主页和桌宠。
- 如果动态形象制作困难，MVP 可以先使用 Q 版卡通形象、静态贴图或简单动画，不让 3D 精细还原阻塞闭环。

## AI 与 Agent 边界

- AI 主入口是陪伴对话，同时异常报告和数据视图也可以触发 AI 分析。
- AI 需要读取宠物档案、当前状态、历史数据、异常、任务和用户记忆。
- 继续沿用成熟 agent 或成熟模型服务原则，不从零写 agent 框架。
- 健康解释要避免变成泛百科，回答必须绑定当前这只宠物的数据。

## 当前 MVP 必须跑通的闭环

1. 启动 AI Pet 后桌宠出现在桌面。
2. 桌宠可以主动气泡或被用户点击。
3. 点击桌宠弹出应用窗口，默认进入陪伴对话主页。
4. 用户能和宠物持续对话，且对话引用宠物档案和记忆。
5. 数据与异常视图展示摄食、运动、睡眠、定位和特殊行为。
6. mock 数据触发至少一个异常，桌宠弹出异常提示。
7. 用户点击异常提示进入异常报告，看到 AI 分析和建议。
8. 用户进入换装/互动视图，给宠物应用一个装扮。
9. 装扮结果同步到对话主页和桌宠。
10. 周期报告或摘要能基于历史数据生成。

## 暂不作为 MVP 核心

- 静态 HTML 展示页、汇报页或营销页。
- 完整登录注册。
- 真实硬件 API 审核。
- 多宠物群聊。
- 医生角色常驻在陪伴私聊中。
- 完整社区、排行榜和电商下单。
- 精细 3D 真实宠物重建。
- 人形角色作为桌面主形象。
