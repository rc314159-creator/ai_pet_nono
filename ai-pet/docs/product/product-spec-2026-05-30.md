# AI Pet 当前产品规格

## 当前定位

AI Pet 是一个 AI 情感陪伴型宠物产品。它不是单纯硬件项圈、单纯医疗问诊、单纯网页控制台，也不是泛桌宠。

产品用“宠物形象”承载四类能力：

1. AI 陪伴和聊天。
2. 真实宠物数据解释和照护任务。
3. 每日任务激励、积分、连续天数和排行榜反馈。
4. 电子宠物养成、状态变化和日常互动。
5. 宠物商品、装扮和服务推荐。

## 主闭环

产品主闭环不是在“AI 电子宠物陪伴”和“真实宠物数字分身”之间二选一。两者共存：

- 电子宠物可以是完全虚拟的 AI 宠物。
- 电子宠物也可以是真实宠物在系统里的数字分身。

当前开发优先级是已养真实宠物的人群，但系统必须兼顾没有真实宠物、只需要电子宠物陪伴的人群。两类用户共享宠物形象、AI 记忆、状态机、互动、桌宠入口和应用窗口入口。

## 用户优先级

### 优先用户：已有真实宠物的人

用户需求：

- 让 AI 理解自己的真实宠物，而不是回答泛宠物百科。
- 把活动、睡眠、抓挠、吠叫、饮食、饮水、位置、库存和照护记录解释成可执行任务。
- 在桌面宠物和其弹出的应用窗口中持续看到宠物状态、提醒和反馈。

必须开发的产品能力：

- 真实宠物档案。
- 设备或 mock 数据绑定。
- 宠物状态机。
- AI 问答与任务规划。
- 桌宠核心入口。
- 商品、护理、装扮或服务推荐。

### 兼顾用户：没有真实宠物但有陪伴需求的人

用户需求：

- 领养或生成一个 AI 电子宠物。
- 通过聊天、喂养、玩耍、清洁、装扮和任务建立陪伴关系。
- 宠物需要有状态变化、成长反馈和记忆，而不是只有聊天皮肤。

必须在架构上兼容的能力：

- 虚拟宠物档案。
- 独立于真实硬件的状态机。
- 互动事件和亲密度。
- 装扮、道具和成长系统。

当前 Demo 可以优先展示真实宠物分身，但不能把纯电子宠物描述为另一个不相关产品。

## MVP 入口形态

项目没有 HTML 展示页，不做静态网页看板、营销页或纯汇报页。

当前 MVP 的产品形态是：

1. 用户先看到系统级桌面宠物。
2. 桌宠常驻桌面，负责气泡、状态、异常提醒和点击入口。
3. 用户点击桌宠后，弹出应用窗口/功能面板。
4. 应用窗口承载陪伴对话、数据监测、异常报告、换装互动、任务和后续商业/社区入口。
5. 用户在应用窗口完成复杂操作后，关键结果同步回桌宠形态、状态或气泡。

技术上应用窗口可以使用 React/Vite 等前端技术渲染，但产品口径统一称为“应用窗口”“功能面板”或“宠物面板”，不能再称为 HTML 展示页。

## 桌宠定位

桌宠不是简单表现层。桌宠必须是核心入口之一。

桌宠应承担：

- 常驻可见的宠物存在感。
- 状态入口：用户无需打开完整应用窗口也能看到今日重点。
- 点击入口：用户点击桌宠后展开应用窗口，进入陪伴对话、数据、异常和换装等功能。
- 轻互动入口：喂食、玩耍、护理、休息、提醒确认等轻动作应能从桌宠触发或反馈到桌宠。
- Agent 输出入口：AI 生成的任务、解释和提醒可通过桌宠气泡、动作和状态表达。

桌宠和点击后弹出的应用窗口必须同时具备。只有独立页面或只有桌宠都不能表达完整产品。

复杂交互不直接堆在桌宠本体上，例如长对话、数据查看、异常分析和换装。它们应在应用窗口完成，并把结果同步回桌宠。

## 桌宠联动口径

桌宠和应用窗口之间有两套联动逻辑，不能混为一谈：

1. 基础跳转逻辑：用户点击桌宠后，桌面程序打开或聚焦应用窗口；点击异常气泡、任务提醒或换装反馈时，可以打开对应页签。
2. 动作联动逻辑：桌宠动作由统一动作仲裁决定，而不是由某个页面直接抢占渲染；对话页只和 agent 对话，运动能力作为接口暴露给 agent。

动作联动的产品优先级为：

1. Agent 动作工具调用最高。例如用户说“请转个圈”，agent 决定调用动作接口后，桌宠应优先执行对应动作。
2. 指令触发的随机动作居中。例如用户轻触、agent 或演示指令要求“随机卖萌一下”，桌宠从动作池中选择动作。
3. 手环/设备数据映射为默认状态。例如动物手环记录真实宠物正在走动、睡觉、进食或抓挠，领域层将其映射为桌宠默认动作。

手环/设备数据是默认底座；agent 的动作工具调用可以临时覆盖它。高优先级动作完成后，桌宠回到最新的手环/设备默认映射。

## 应用窗口信息架构

点击桌宠后应用窗口先进入欢迎/介绍初始页，包含“毛球伙伴”和“开始陪伴”按钮；用户点击“开始陪伴”后进入陪伴对话主页。MVP 应用窗口底部导航按参考 App 对齐为 5 个主入口：

- 市集：商品、护理用品、装扮道具和后续商业推荐入口。
- 社区：宠物内容、照护经验和后续社区入口。
- 陪伴对话：开始陪伴后的默认主页，一个宠物对应一个连续对话上下文，需要维护用户记忆和宠物记忆。
- 状态与数据：今日状态、摄食、运动、睡眠、定位、特殊行为、护理记录、异常报告和健康建议；异常提示从桌宠进入这个状态/数据页。
- 我的：宠物档案、宠物知识库入口、用户激励入口、我的装扮区、个人设置和与桌宠外观同步的操作。用户激励只在“我的”页放入口，不在首页堆完整任务、排行榜和奖励清单；装扮区仍属于“我的”页既有功能，不因为用户激励拆成同级入口集合。

每日任务不是静态清单。当前 Demo 需要展示“完成任务获得积分、连续照护天数、排行榜反馈、奖励/服饰解锁”的用户激励闭环；完整开放社区可以后置，但任务积分、轻量排行榜和奖励进度不能缺失。用户从“我的”页点击“用户激励”进入独立用户激励页；用户激励页下继续进入“每日任务”详情页、“排行榜”详情页和“奖励/可解锁服饰”详情页。每日任务页必须展示任务完成/未完成状态、任务原因、时间窗口和积分；排行榜条目必须可点击查看明细；任何装扮页中标注“奖励获得”的服饰或配饰，都必须在奖励页展示对应解锁来源和当前进度。

当前展示阶段即使使用 mock 数据，也应做成可点击原型，而不是静态看板：市集分类和商品详情、社区搜索和帖子详情、状态日期和健康报告、我的页用户激励入口、每日任务完成、排行榜点击、奖励解锁来源、装扮分类与保存都需要有可见交互反馈。

应用窗口视觉比例应接近手机屏幕长宽比，当前 demo 按约 `430x932` 的竖向比例设计，不使用宽屏桌面控制台比例。

陪伴对话主页应是类似微信的上下文聊天窗口：只承载连续聊天、语音/输入和宠物背景氛围。真实宠物分身在对话页作为背景板呈现，不作为左右分栏侧边栏；今日状态、数据卡片和异常报告不混入对话主页。

健康问答、异常分析和问诊入口优先挂在状态与数据视图中；陪伴对话主页以人和宠物的情感交流为主。

### 对话页 Agent 口径

对话页是单宠物唯一长期主群聊，不是普通双人问答框，也不是每次创建新 session 的聊天页。一个宠物只对应一个主群聊 thread；技术层可以有多个 Agent run、临时语音连接或工具执行，但都必须归档到同一个主 thread。

当前 Demo 的群聊可见宠物名字和头像必须来自同一份 `PetProfile` 显示身份；当前应用窗口资料显示名为“旺财”，头像与“我的”页一致。默认用户角色为“主人”。后续用户可以自定义宠物角色、声音和成员，但不能让对话页和“我的”页各自维护一套名字/头像。

对话页必须满足三条用户体验要求：

- 长期记忆：能恢复之前群聊消息，并能记住主人明确说过的照护安排、偏好和承诺。
- 主动沟通：用户每次进入对话页时，如果宠物状态、异常、库存或待办有问题，宠物要主动开口，例如用狗狗视角说“我身体不太舒服”“肚皮有点痒”。
- 狗狗语气：当前 Demo 宠物是狗狗“旺财”，发言要像狗狗和主人说话，不能像客服、诊断机器人或普通 AI 助手。

文字和语音是两种输出模式：

- 用户要求文字回复时，Agent 返回文字群聊消息。
- 用户要求语音回复时，Agent 调用语音回复工具，返回语音群聊消息，可附 transcript 作为记录。

语音不是所有文字消息的后处理。只有当前回合选择或请求语音时，才走语音工具。

## 多端入口

多端入口是产品要求，不是可有可无的展示概念。

当前开发优先级：

1. 系统级桌面宠物。
2. 桌宠点击后弹出的应用窗口/功能面板。

当前工作分工：

- 桌面端宠物形象、动作、照片级素材和桌宠运行表现由独立进程/独立开发线处理。
- 本应用窗口侧只负责用户点击桌宠后打开的应用窗口/功能面板，包括对话、状态与数据、换装入口、任务和报告。
- 应用窗口中的宠物形象只作为页面视觉占位或背景氛围，不在本线投入真实桌宠形象制作；后续由桌宠形象进程与应用窗口入口联动。

这个分工不改变当前可运行 Demo 的入口事实：完整链路默认由 `desktop-photo-pet` Electron 进程创建桌宠窗口，并在用户点击桌宠时创建或聚焦应用窗口；React/Vite 只负责该应用窗口的 renderer。

后续再讨论并择优接入：

- 移动端 H5/PWA。
- 飞书、微信或其他通讯软件入口。
- 微信小程序。
- 手机 App。

所有端都应复用同一套领域服务、状态机、Agent tools 和数据契约，不为每个端重写业务逻辑。

## AI 与 Agent 原则

凡是涉及 AI 的地方，优先接成熟 agent、成熟模型服务或成熟工具协议，不从零写 agent 框架。

当前方向：

- 当前对话主路径是 OpenCode/opencode runtime + `ai_pet` MCP tools；项目侧负责宠物业务工具、数据契约、状态机、UI 和端入口。
- OpenAI Agents SDK 只作为 fallback，不能描述为最终 Agent 底座。
- 当前 Demo 的模型供应商使用 llmmelon OpenAI-compatible Chat Completions；模型供应商和 Agent runtime 是两层，llmmelon 只负责底层模型调用，不替代成熟 Agent runtime。
- 宠物业务能力通过 MCP tools 或等价工具协议交给成熟 Agent runtime 调用。
- 由 agent 调用业务工具完成群聊回复、memory 写入、任务规划、桌宠动作、语音回复和推荐。
- 当前 Demo 的语音回复工具优先使用阿里云百炼 Qwen：`qwen-voice-design` 生成科技狗音色，`qwen3-tts-vd-2026-01-26` 合成当回合语音。
- 项目只开发宠物业务工具、数据契约、状态机、UI 和端入口。

AI Key 和算力不是当前开发限制；用户已明确有可用 API Key 和 8 张 4090 可用。

## 商业与装扮

电商和换装的落地方式由开发侧负责调研和执行，不能反复要求用户给出完整方案。

当前可执行方向：

- MVP 先做装扮和道具系统，用内置模板满足娱乐和陪伴玩法；但当前展示阶段的真实桌宠换装只承诺三个配饰项。
- 当前“我的装扮”里的服装、毛发、妆容只作为应用窗口预览或后续方案，不描述为已真实同步到桌宠。
- 如果装扮项文案写“奖励获得”“连续照护解锁”或类似来源，必须在“用户激励 -> 奖励/可解锁服饰”中看到对应奖励项、解锁条件和进度；装扮页只消费解锁状态，不承担解释奖励体系。
- 当前真实同步目标是照片级 Mochi 桌宠动作帧：每个可选配饰都需要为每张桌宠帧图生成一张新的完整宠物图片，运行时按当前配饰状态切换整套完整帧。
- 配饰换装结果同步到陪伴对话主页和桌宠；对话主页和应用窗口预览必须以桌宠照片级形态为标准，不再回到卡通小狗作为真实换装对象。
- 库存、健康、任务触发商品推荐作为后续商业化入口预留。
- 真实宠物试装或同款推荐作为增强方向。
- 商品推荐必须接入宠物档案、过敏、年龄、体重、任务和库存上下文。

## 当前不作为开发讨论焦点

- 不讨论多版本路线；当前目标是明天可运行的项目展示 Demo。
- 不把安全边界作为当前产品讨论焦点；相关底线可保留在实现中，但不作为当前要用户拍板的问题。
- 不等待真实硬件授权或 API 审核；Demo 可以用完整 mock 数据和手动数据跑通产品闭环。
- 不做展陈页或 PPT 包装作为核心任务；当前核心任务是开发。
