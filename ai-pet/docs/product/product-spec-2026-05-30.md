# AI Pet 当前产品规格

## 当前定位

AI Pet 是一个 AI 情感陪伴型宠物产品。它不是单纯硬件项圈、单纯医疗问诊、单纯网页控制台，也不是泛桌宠。

产品用“宠物形象”承载四类能力：

1. AI 陪伴和聊天。
2. 真实宠物数据解释和照护任务。
3. 电子宠物养成、状态变化和日常互动。
4. 宠物商品、装扮和服务推荐。

## 主闭环

产品主闭环不是在“AI 电子宠物陪伴”和“真实宠物数字分身”之间二选一。两者共存：

- 电子宠物可以是完全虚拟的 AI 宠物。
- 电子宠物也可以是真实宠物在系统里的数字分身。

当前开发优先级是已养真实宠物的人群，但系统必须兼顾没有真实宠物、只需要电子宠物陪伴的人群。两类用户共享宠物形象、AI 记忆、状态机、互动、桌宠入口和应用窗口入口。

## 用户优先级

### 优先用户：已有真实宠物的人

用户需求：

- 让 AI 理解自己的真实宠物，而不是回答泛宠物百科。
- 把活动、睡眠、抓挠、吠叫、饮食、饮水、位置、库存和照护记录解释成可执行任务。
- 在桌面宠物和其弹出的应用窗口中持续看到宠物状态、提醒和反馈。

必须开发的产品能力：

- 真实宠物档案。
- 设备或 mock 数据绑定。
- 宠物状态机。
- AI 问答与任务规划。
- 桌宠核心入口。
- 商品、护理、装扮或服务推荐。

### 兼顾用户：没有真实宠物但有陪伴需求的人

用户需求：

- 领养或生成一个 AI 电子宠物。
- 通过聊天、喂养、玩耍、清洁、装扮和任务建立陪伴关系。
- 宠物需要有状态变化、成长反馈和记忆，而不是只有聊天皮肤。

必须在架构上兼容的能力：

- 虚拟宠物档案。
- 独立于真实硬件的状态机。
- 互动事件和亲密度。
- 装扮、道具和成长系统。

当前 Demo 可以优先展示真实宠物分身，但不能把纯电子宠物描述为另一个不相关产品。

## MVP 入口形态

项目没有 HTML 展示页，不做静态网页看板、营销页或纯汇报页。

当前 MVP 的产品形态是：

1. 用户先看到系统级桌面宠物。
2. 桌宠常驻桌面，负责气泡、状态、异常提醒和点击入口。
3. 用户点击桌宠后，弹出应用窗口/功能面板。
4. 应用窗口承载陪伴对话、数据监测、异常报告、换装互动、任务和后续商业/社区入口。
5. 用户在应用窗口完成复杂操作后，关键结果同步回桌宠形态、状态或气泡。

技术上应用窗口可以使用 React/Vite 等前端技术渲染，但产品口径统一称为“应用窗口”“功能面板”或“宠物面板”，不能再称为 HTML 展示页。

## 桌宠定位

桌宠不是简单表现层。桌宠必须是核心入口之一。

桌宠应承担：

- 常驻可见的宠物存在感。
- 状态入口：用户无需打开完整应用窗口也能看到今日重点。
- 点击入口：用户点击桌宠后展开应用窗口，进入陪伴对话、数据、异常和换装等功能。
- 轻互动入口：喂食、玩耍、护理、休息、提醒确认等轻动作应能从桌宠触发或反馈到桌宠。
- Agent 输出入口：AI 生成的任务、解释和提醒可通过桌宠气泡、动作和状态表达。

桌宠和点击后弹出的应用窗口必须同时具备。只有独立页面或只有桌宠都不能表达完整产品。

复杂交互不直接堆在桌宠本体上，例如长对话、数据查看、异常分析和换装。它们应在应用窗口完成，并把结果同步回桌宠。

## 应用窗口信息架构

点击桌宠后默认进入陪伴对话主页。MVP 应用窗口保留 3-4 个主入口：

- 陪伴对话：默认主页，一个宠物对应一个连续对话上下文，需要维护用户记忆和宠物记忆。
- 数据与异常：展示摄食、运动、睡眠、定位、特殊行为和护理记录；异常提示从桌宠进入异常报告。
- 换装/互动：使用内置模板进行装扮和简单互动，结果同步到对话主页和桌宠。
- 社区/商业：当前只做入口预留或轻量展示，不阻塞 MVP。

健康问答、异常分析和问诊入口优先挂在数据与异常视图中；陪伴对话主页以人和宠物的情感交流为主。

## 多端入口

多端入口是产品要求，不是可有可无的展示概念。

当前开发优先级：

1. 系统级桌面宠物。
2. 桌宠点击后弹出的应用窗口/功能面板。

后续再讨论并择优接入：

- 移动端 H5/PWA。
- 飞书、微信或其他通讯软件入口。
- 微信小程序。
- 手机 App。

所有端都应复用同一套领域服务、状态机、Agent tools 和数据契约，不为每个端重写业务逻辑。

## AI 与 Agent 原则

凡是涉及 AI 的地方，优先接成熟 agent、成熟模型服务或成熟工具协议，不从零写 agent 框架。

当前方向：

- 使用 OpenCode SDK / opencode agent runtime 作为成熟 agent 能力入口。
- 通过 MCP 或等价工具协议暴露宠物业务工具。
- 由 agent 调用业务工具完成问答、任务规划、桌宠反馈和推荐。
- 项目只开发宠物业务工具、数据契约、状态机、UI 和端入口。

AI Key 和算力不是当前开发限制；用户已明确有可用 API Key 和 8 张 4090 可用。

## 商业与装扮

电商和换装的落地方式由开发侧负责调研和执行，不能反复要求用户给出完整方案。

当前可执行方向：

- MVP 先做虚拟宠物装扮和道具系统，用内置模板满足娱乐和陪伴玩法。
- 换装结果同步到陪伴对话主页和桌宠。
- 库存、健康、任务触发商品推荐作为后续商业化入口预留。
- 真实宠物试装或同款推荐作为增强方向。
- 商品推荐必须接入宠物档案、过敏、年龄、体重、任务和库存上下文。

## 当前不作为开发讨论焦点

- 不讨论多版本路线；当前目标是明天可运行的项目展示 Demo。
- 不把安全边界作为当前产品讨论焦点；相关底线可保留在实现中，但不作为当前要用户拍板的问题。
- 不等待真实硬件授权或 API 审核；Demo 可以用完整 mock 数据和手动数据跑通产品闭环。
- 不做展陈页或 PPT 包装作为核心任务；当前核心任务是开发。
