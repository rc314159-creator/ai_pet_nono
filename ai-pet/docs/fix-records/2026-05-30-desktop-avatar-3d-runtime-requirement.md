# 真实宠物桌宠形象需 3D 桌面运行时问题记录

日期：2026-05-30

## 事实时间线

- 用户要求查看“桌面端真实宠物怎么展示，足够真实怎么做”，并强调“只需要展示桌面形象”。
- 上一轮实现了 `reports/desktop-pet-avatar-demo/index.html` 和半写实透明 PNG，用浏览器模拟桌面浮窗。
- 上一轮知识库将当前 Demo 路线写成“半写实 2D/2.5D sprite -> OpenPets pet pack”。
- 用户随后纠偏：目标不是前端 HTML，而是桌面端运行程序；展示方式希望是 3D；宠物需要能动；整体链路是用户上传照片后生成对应宠物，当前可以先不实现中间生成逻辑，但要先做出 3D 形象。

## 证据引用

- 用户原话：希望“用 3D 的方式来展示”，“不是前端 HTML，而是桌面端的运行程序，能够直接在桌面上显示”，“要能够让它动起来，是 3D 能动的”，“根据用户上传的照片，生成这种对应的宠物”。
- `ai-pet/docs/research/desktop-real-pet-avatar-2026-05-30.md`：上一轮写入了 2D/2.5D sprite 路线，和用户最新要求冲突。
- `reports/desktop-pet-avatar-demo/index.html`：上一轮只是浏览器/HTML 视觉原型，不满足桌面运行程序要求。

## 根因

把会议里“当前开源项目精细度不够，第一版不能阻塞完整 3D 建模”错误收敛成“当前主路线用 2D/2.5D sprite”。用户实际要求是：展示层先按 3D 桌面运行时做，即使照片到 3D 的生成链路暂时用占位模型，也不能把桌面形象降级成前端 HTML 或 2D 图。

## 修复计划

1. 更新真实宠物桌面形象路线：3D 桌面运行程序为当前目标；2D sprite 只作为 fallback，不作为主路线。
2. 新增可运行桌面端 3D Demo：透明/无边框桌面窗口，显示可动画的 3D 宠物形象。
3. 记录照片到 3D 的产品链路：照片上传 -> 宠物身份特征提取 -> image-to-3D/mesh 生成或模板拟合 -> rig/动作绑定 -> 桌面运行时加载。
4. 明确 OpenPets 的边界：若 OpenPets 当前 pet pack 仍以 sprite 为主，则它不能单独满足 3D 形象要求；需要扩展 renderer 或采用 Electron/Tauri/Unity/Godot/Three.js 等 3D 桌面运行时。
