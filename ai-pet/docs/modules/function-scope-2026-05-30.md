# AI Pet 功能范围与对齐问题

## 使用原则

开发对齐必须先按功能域拆解，而不是先按团队、展陈或 PPT 叙事拆解。每个功能域都要明确：

1. 要不要做。
2. 具体做哪些功能。
3. 哪些必须跑通。
4. 哪些可以 mock 或只做入口。
5. 前端、后端、Agent、商业化分别依赖什么。

## 功能大类总览

| 功能大类 | 优先级 | 核心目标 |
|---|---:|---|
| 宠物创建与身份系统 | P0 | 同时支持真实宠物数字分身和纯电子宠物 |
| 桌面宠物核心入口 | P0 | 桌宠作为常驻主入口，负责气泡、状态、异常提示和点击展开 |
| 应用窗口/功能面板 | P0 | 点击桌宠后弹出，承载陪伴对话、数据异常、换装互动、任务和后续推荐 |
| AI Agent 智能交互 | P0 | 用成熟 agent 调用宠物业务工具 |
| 数据接入与证据流 | P0 | 把设备、手动、互动、库存等事件统一成证据 |
| 宠物状态与养成系统 | P0 | 让真实分身和电子宠物都有状态变化和关系积累 |
| 照护任务与健康解释 | P0 | 从数据生成任务、解释和提醒 |
| 用户激励、任务积分与奖励 | P0 | 把每日任务完成转成积分、连续天数、排行榜和奖励/服饰解锁反馈 |
| 商品推荐与换装 | P1 | MVP 先做内置模板换装，商业推荐作为后续入口 |
| 多端入口 | P1 | 在桌宠 + 应用窗口外预留 H5/PWA、通讯软件、小程序、App |
| 记忆与个性化 | P1 | 保存用户偏好、宠物习惯和历史互动 |
| 社区、挑战与分享 | P2 | 提供社区感、排行榜和分享内容 |
| 系统运行与验证 | P0 | 保证一键启动、可观测、可验证、可演示 |

## 1. 宠物创建与身份系统

具体功能：

- 创建宠物：选择“真实宠物分身”或“纯电子宠物”。
- 宠物档案：名字、物种、品种、年龄、体重、性别、过敏、病史、饮食、外观。
- 电子宠物设定：形象、人设、性格、初始状态、成长偏好。
- 宠物形象：照片、头像、桌宠 pet pack、颜色/装扮。
- 宠物切换：多宠物列表、当前激活宠物。

待确认：

- 真实宠物和电子宠物是否共用同一个创建流程？
- Demo 是否必须支持“创建新宠物”，还是先内置样例宠物？
- 是否必须支持猫狗之外的宠物？
- 专属桌宠形象是否必须在当前 Demo 完成？

MVP 已确认：

- 先支持猫狗。
- 真实宠物和电子宠物核心差异只在数据来源；窗口、对话、状态和桌宠表达共用。
- MVP 默认一人一只当前宠物，多宠物只预留。

## 2. 桌面宠物核心入口

具体功能：

- 系统级桌宠窗口：启动、显示、隐藏、置顶、状态检测。
- 桌宠气泡：主动提醒、Agent 回复、任务提示、异常提示。
- 桌宠状态：开心、疲惫、饥饿、清洁、警告、庆祝、等待。
- 桌宠交互：点击、菜单、确认提醒、触发轻量喂食/玩耍/护理/休息。
- 点击展开：点击桌宠后弹出应用窗口/功能面板。
- 异常跳转：桌宠异常提示可打开异常报告视图。
- 应用窗口联动：窗口操作同步到桌宠，桌宠事件反向更新窗口。

待确认：

- 当前 OpenPets built-in pet 是否可接受，还是必须替换为项目宠物形象？
- 当前 Demo 桌宠必须支持哪些交互动作？
- 桌宠主动提醒频率和触发条件是什么？
- 桌宠是否要作为 Agent 聊天入口？

MVP 已确认：

- 桌宠本体只承担展示、点击入口和轻交互。
- 长对话、数据查看、异常分析和换装放在点击后弹出的应用窗口中。
- 换装或状态变化后要同步回桌宠。

## 3. 应用窗口/功能面板

具体功能：

- 陪伴对话主页：点击桌宠后的默认页面，一个宠物一个连续对话上下文。
- 宠物形象区：显示宠物形象、当前状态和装扮结果。
- 数据面板：摄食、运动、睡眠、定位、特殊行为、护理记录和异常标记。
- 异常报告：异常原因、历史数据、AI 分析、处理建议和确认/忽略。
- 今日任务面板：任务列表、完成状态、原因解释。
- 换装/互动面板：服装、帽子、鞋子、配饰、简单装饰模板。
- AI 问答面板：围绕当前宠物数据问答，但健康异常优先挂在数据/异常上下文。
- 商品/推荐入口：推荐原因、适配条件、操作入口，当前可预留。
- 桌宠连接面板：连接状态、同步到桌宠、错误提示。

待确认：

- 应用窗口首页优先展示宠物、数据、任务还是聊天？
- 当前 Demo 是否需要宠物创建/编辑表单？
- 移动端响应式是否进入当前必须验收？
- 应用窗口是否需要保留社区/挑战入口？

MVP 已确认：

- 默认主页是陪伴对话，不是数据看板。
- 底部或等价导航保留陪伴对话、数据与异常、换装/互动、后续社区/商业入口。
- 当前没有 HTML 展示页；应用窗口是产品功能面板，不是汇报页面。

## 4. AI Agent 智能交互

具体功能：

- Agent 对话：用户问宠物状态、照护、库存、任务、推荐。
- Agent 工具调用：读档案、读状态、读证据、生成任务、记录互动、触发桌宠、生成推荐。
- Agent 主动能力：发现异常后生成提醒或任务。
- Agent 角色表达：专业照护助手、宠物拟人表达或二者混合。
- Agent 运行接入：OpenCode SDK / opencode runtime + MCP 或等价工具协议。

待确认：

- 当前 Demo Agent 必须接到哪些工具？
- Agent 回复是“宠物自己说话”，还是“照护助手解释”？
- Agent 是否要主动推送，还是只响应用户输入？
- OpenCode SDK / opencode runtime 的具体接入方式由哪条路径实现？

MVP 已确认：

- 对话要维护用户记忆和宠物记忆。
- 宠物可以在异常、长期未互动或陪伴场景下主动说话。
- 陪伴私聊以宠物为主，不把医生角色常驻混入私密对话。
- 健康问答和问诊入口优先从异常报告或数据视图进入。

## 5. 数据接入与证据流

具体功能：

- Mock 设备数据：活动、睡眠、心率、呼吸、体温、GPS/定位、安全围栏、抓挠、舔毛、吠叫。
- 摄食数据：食物类型、进食量、进食速度、进食频率，可来自硬件假设、喂食设备或人工输入。
- 手动记录：喂食、饮水、用药、护理、洗澡、伤口观察、情绪观察。
- 库存事件：主粮、零食、清洁用品、玩具、药品、装扮。
- 互动事件：喂食、玩耍、护理、休息、聊天、桌宠点击。
- 证据时间线：统一记录来源、时间、指标、解释和关联任务。

待确认：

- 当前 Demo 必须展示哪些设备指标？
- 是否需要支持照片/视频引用？
- 数据是前端 mock、后端 mock，还是文件/数据库存储？
- 哪些事件必须影响宠物状态？

MVP 已确认：

- 原始数据以时间序列为主，AI 解释和二级指标从原始数据归纳。
- 用户看到的是正常/异常/需要关注，而不是原始数据流水账。
- 护理、洗澡、用药等可以依赖人工日历和手动记录。

## 6. 宠物状态与养成系统

具体功能：

- 基础状态：饱腹、心情、精力、清洁、亲密度。
- 健康/行为标记：活动低、睡眠差、抓挠多、围栏异常、压力高。
- 状态变化：设备数据、手动记录、互动、任务完成都会影响状态。
- 纯电子宠物养成：成长、等级、冷落反馈、偏好、装扮收益。
- 桌宠表达映射：状态映射到动作、气泡和提醒。

待确认：

- 当前 Demo 状态指标固定为哪些？
- 状态变化规则要精确到什么程度？
- 纯电子宠物是否需要独立成长线？
- 是否需要状态衰减和时间流逝机制？

MVP 已确认：

- 数据变化必须能影响桌宠形态，例如睡觉、疲惫、异常警告、开心等。
- 纯电子宠物也要有算法生成或互动驱动的数据，避免数据页为空。

## 7. 照护任务与健康解释

具体功能：

- 今日任务：喂食、换水、遛狗、清洁、护理、休息、陪玩、补货。
- 任务生成：规则生成 + Agent 解释/排序。
- 异常解释：活动下降、睡眠差、抓挠增加、位置异常、库存不足。
- 异常报告：每条异常至少对应 AI 分析和处理建议。
- 报告：单日摘要、趋势摘要、周报/月报。
- 提醒：应用窗口、桌宠、后续多端推送。

待确认：

- 当前 Demo 必须有哪些任务类型？
- 健康解释做到单日，还是要周报/月报？
- 是否需要“给兽医/家人看的摘要”？
- 任务由规则主导还是 Agent 主导？

MVP 已确认：

- 通知的是异常，不是孤立建议。
- 建议挂在异常报告下，可确认、忽略或标记已处理。
- 至少支持进食量变化、长时间未进食、运动量明显下降、睡眠异常、特殊行为频率异常、位置异常等 demo 规则。

## 7.1 用户激励、任务积分与排行榜

具体功能：

- 每日任务积分：完成喂食、换水、遛狗、护理、补货、训练等任务后获得积分。
- 连续天数：连续完成每日照护任务形成 streak。
- 排行榜：按任务完成积分、连续天数或挑战主题展示当前宠物排名。
- 成就反馈：完成高优先级任务后可以在应用窗口和后续桌宠气泡中反馈。
- 奖励/服饰解锁：按连续天数、积分、完成任务数、排名或特定任务解锁服饰、配饰、徽章或道具。

当前 Demo 已确认：

- “我的页中的用户激励入口 -> 用户激励页 -> 每日任务详情 -> 点击完成 -> 获得积分 -> 排行榜详情高亮当前宠物 -> 奖励/可解锁服饰展示进度”是用户激励闭环，不属于可延后的完整社区功能。
- “我的”页只放“用户激励”入口，不把完整每日任务、排行榜和奖励清单堆在首页。
- “我的”页仍保留宠物档案、宠物知识库和装扮功能；不能因为新增用户激励，把装扮也做成同级入口集合。
- 每日任务详情页必须展示完成/未完成状态、任务说明、时间窗口和积分；排行榜详情页的排名条目必须可点击查看明细；奖励页必须展示奖励来源、解锁条件和当前进度。
- 装扮页中任何“奖励获得”的服饰或配饰，都必须在用户激励奖励页有对应解锁来源。
- 完整开放社区和真实比赛运营可后置；排行榜可以先用 mock 社区数据，但当前宠物积分必须随任务完成变化。

## 8. 商品推荐与换装

具体功能：

- 库存管理：剩余量、剩余天数、阈值、补货提醒。
- 商品推荐：主粮、零食、护理用品、玩具、药品、服装、服务。
- 推荐触发：库存不足、任务需要、状态异常、装扮需求。
- 换装：MVP 先做电子宠物装扮，真实宠物照片试装和同款推荐后续增强。
- 换装模板：服装、帽子、鞋子、配饰、简单妆容或装饰。
- 推荐卡片：原因、适配条件、禁忌检查、操作入口。

待确认：

- 当前 Demo 商业化最小闭环选哪一种？
- 换装先做电子宠物换装，还是真实宠物试装？
- 商品库使用 mock、人工配置还是真实 API？
- 是否需要购买按钮或只做推荐入口？

MVP 已确认：

- 换装是娱乐和陪伴玩法，不是当前商品页面。
- 宠物核心身份固定，尤其真实宠物分身不随意改变五官、体型和基础形象。
- 换装结果必须同步到陪伴对话主页和桌宠。

## 9. 多端入口

具体功能：

- 当前必做：系统级桌宠 + 点击桌宠弹出的应用窗口/功能面板。
- 移动 H5/PWA：查看状态、任务、聊天、推荐。
- 通讯软件：飞书/微信聊天、任务卡片、提醒。
- 小程序/App：宠物状态、任务、聊天、推荐、绑定。

待确认：

- 应用窗口 + 桌宠之后，哪个端口优先？
- 通讯软件是只聊天，还是要任务卡片？
- 移动端是否需要当前 Demo 验收？
- 多端是否共用账号和宠物状态？

## 10. 记忆与个性化

具体功能：

- 用户偏好：称呼、提醒频率、商品偏好、禁忌。
- 宠物习惯：作息、食量、活动基线、互动偏好。
- 聊天记忆：重要对话、承诺、历史问题。
- 推荐记忆：已推荐、已忽略、已购买、已完成。

待确认：

- 当前 Demo 是否需要持久化记忆？
- 记忆保存在哪：本地、后端、文件、数据库？
- Agent 每次回答需要注入哪些记忆？

## 11. 社区、挑战与分享

具体功能：

- 挑战：运动、护理、训练、陪伴连续天数。
- 排行榜：宠物状态、任务完成、活动量。
- 分享卡：今日宠物报告、任务完成、装扮效果。
- 社区入口：后续宠友、比赛、活动。

待确认：

- 当前 Demo 是否保留社区面板？
- 挑战是静态展示还是可互动？
- 分享是否需要真实生成图片/卡片？

## 12. 系统运行与验证

具体功能：

- 一键启动：应用窗口、API、桌宠、Agent tools。
- 运行状态：健康检查、桌宠连接状态、Agent 连接状态。
- 错误兜底：OpenPets 未启动、Agent 失败、数据缺失。
- 验证脚本：类型检查、构建、API 测试、应用窗口 E2E（开发期可用浏览器驱动验证）、桌宠观察。
- Demo 数据：稳定可复现的样例宠物、数据包、任务、推荐。

待确认：

- 当前标准启动命令是什么？
- 什么算全流程跑通？
- 哪些失败必须前端可见？
- 验收截图/日志保存到哪里？
